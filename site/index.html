Give an agent a Git commit and a target. Gantry previews the actions, runs them on your machines, and saves the results under a durable run ID.

Build a pinned revision

revision=$(git rev-parse HEAD)
run_id="check-$(date +%s)"

gantry plan "$run_id" owner/project "$revision" check
gantry run "$run_id" owner/project "$revision" check
gantry watch "$run_id"

Workflow

Build a revision.
Submit a group.

Both use the same action graph. Submission uses a passing run to authorize a guarded Git update.

›_ Ordinary build

Run a target against a pinned revision. Inspect per-action status and fetch logs or artifacts by digest. Check back later with the same run ID.

gantry run <id> <repo> <commit> <target>

↳ Guarded submit

Submit PRs in order. Gantry pins their heads, builds a combined commit, and uses the tested base SHA to guard the target update.

gantry submit <id> <repo> <pr> [<pr> ...]

Runtime

A shared queue.
Your machines.

Route registered projects to named worker pools. When an action’s definition, image, inputs, and upstream artifacts match, Gantry can reuse its result across commits.

Controllers

Khepri and Ra replicate the queue, including run state, leases, and submit intents.

↕ Claims and results

Worker pools

Docker actions on your hosts. A local SQLite journal tracks custody and lets a worker replay results.

↕ Bytes by digest

Blob store

Shared storage for input snapshots, logs, and artifacts, addressed by SHA-256.

↕ Fetch and update

Git remote

Supplies commits and checks the expected target SHA when Gantry pushes.

Get started

Run it locally.

On Linux, install the pinned toolchain and Docker prerequisites, then run the end-to-end check. It starts three controllers and a Docker worker, and exercises failover, action reuse, and exact-commit landing against a local bare Git remote.

GitHub provider verification has covered builds. Live GitHub landing and PR reconciliation still need deployment validation.
