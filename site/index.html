Self-hosted builds and tested merges for coding agents

Builds and merges your agents run on your own machines.

An agent hands over a Git commit and a target. Gantry shows the action graph it will run, runs it on your Docker workers, and keeps the results under a run ID the agent picks.

When a group of PRs is ready, Gantry tests their combined commit and lands that exact commit, only if the target branch still points at the base it was tested on.

01 Workflow

Build a revision. Submit a group.

Both go through the same action graph. A build reports on a revision. A submission uses a passing build of the combined commit to authorize a guarded Git update.

Build

Run a target against a full commit SHA. Each action declares its inputs and runs in Docker with no network. Status is per action, and logs and artifacts are fetched by SHA-256 digest. Retry or check back later with the same run ID.

A declared action whose definition, image, input files and upstream outputs match an earlier result in the same repository is reused, even across commits.

gantry run ID REPO SHA TARGET

Submit

Name PRs in order. Gantry pins their heads, builds their combined commit on the target branch, and runs the required actions on it. A group queued behind another builds on the tip the first one lands.

If the target moves before the push, the group ends blocked and nothing lands. You submit again, under a new run ID, to test against the new tip.

gantry submit ID REPO PR [PR ...]

02 Guarded submit

The commit that passed is the commit that lands.

Before pushing, Gantry fetches the target and checks that it still points at the tested base. The push itself is a single ref update with that base as the expected old value, so if the branch moves after the check, Git refuses it. A branch that moved during the build can't receive an untested combination.

The intent to land is committed to the replicated queue before the push. If a push ends with an unclear result, the same intent is replayed, and a candidate that is already on the target is recorded as landed instead of pushed again.

03 Runtime

A replicated queue and workers on your hosts.

Controllers share one queue through Khepri and Ra. Runs, leases, proofs and landing intents live there. One controller is enough on a single host; with three, losing one loses no work.

Workers pull. Each worker slot asks for an action, runs it in Docker, and records the result in a local SQLite journal before cleaning up, so a restarted slot replays its result rather than running the action again. A lease that lapses goes to another slot.

Each repository routes its actions to one named pool. A slot runs one action at a time; a large host can run several slots.

04 Checks

How it is tested, and what it doesn't do yet.

TLA+ model
Waiting groups, claims, lease expiry and reassignment, late results, and guarded landing. TLC explores 109,896 distinct states.
Seeded simulation
The production queue transitions against virtual controllers, workers and a Git ref. A sweep of 1,000 seeds, each run twice, reports no safety or liveness violation.
make e2e
Three real controllers, a Docker worker and a bare Git remote. It kills controllers, replays worker results, reuses actions, and lands and blocks a group.
Live GitHub
A pilot landed a group on a disposable, unprotected branch, and GitHub marked its PRs merged. Protected-branch rules have not been piloted.

Not built yet

  • Cancelling a run or a landing.
  • Priority, quotas or reservations. Slots take work first-fit, oldest run first, with no fairness across repositories.
  • Automatic resubmission after the target moves.
  • Garbage collection of blobs.
  • Throughput past about 20 actions per second (4 vCPUs, 100 repositories).

05 Get started

Run it on one Linux host.

Install the toolchain and Docker, then build and install the bundled release. gantry init --local creates a private profile, runs a smoke build in Docker, and prints its run ID and artifact digest.

Contributors can run make e2e for the three-controller fixture.
